# ドキュメントレビュー

```text
/review-docs [<ファイル>...]   # 省略時は docs/**/*.md
```

公開ドキュメント（`sphinx-docs/user/`・`sphinx-docs/dev/`）は指定されたときだけ対象にする。

## 手順

1. 対象を決め、`CLAUDE.md` でプロジェクトの目的・構成・規約・ドキュメント方針（`.claude/rules/documentation.md`）を把握する。
2. 各ドキュメントを読み、5 観点を 1〜5 点で採点する（5 = 問題なし、3 = 主要部は良いが不足・曖昧さあり、1 = 骨格のみ / 信頼できない）:
   - **完全性**: 目的・スコープ・前提・制約・依存がある。TBD / TODO が残っていない。想定読者に必要な情報が揃う
   - **明確性**: 用語が一貫し初出で定義される。具体例・図がある。「適宜」「必要に応じて」「など」に頼らない
   - **一貫性**: 文書内・文書間で矛盾しない。型名・API・パス・コマンドを Grep でコードと照合する。日付・バージョンが最新
   - **実装可能性**: 型・挙動・手順がそのまま使える具体性。存在しないライブラリや非推奨 API を参照しない。手順で再現できる
   - **測定可能性**: 成功基準・受入条件がテスト可能な形で書かれている。数値目標には測定方法がある
3. レポートを出す。

## レポート

```markdown
### 評価サマリー
| ドキュメント | 完全性 | 明確性 | 一貫性 | 実装可能性 | 測定可能性 | 総合 |   ← 総合 = 平均（小数第 1 位）
### 良い点
- **<ファイル>**: どの記述が良いか
### 指摘事項
#### [必須|推奨] タイトル
- 対象: ファイル > セクション / 基準 / 理由 / 改善案
- 改善前: 現在の記述（引用） / 改善後: 提案
### 改善の優先順位
1. [必須] 実装ブロッカー → 2. [必須] 誤解リスク → 3. [推奨] 品質向上 → 4. [推奨] 体裁
```

**[必須]** = 実装に支障がある、または誤解を招く。**[推奨]** = 無くても実装できる改善。
